# Proposal: самообслуживание для follower-аккаунтов CGM

**Дата:** 17.08.2026 · **Статус:** proposal, до кода · **Контекст:** [ADR-0005](../architecture/decisions/0005-cgm-librelinkup-integration.md), [research 14.06](2026-06-14-cgm-librelinkup-integration.md), PR #317

---

## Проблема

Сейчас follower-аккаунт LibreLinkUp задаётся только через окружение: `LLU_EMAIL`/`LLU_PASSWORD` (primary) и `LLU_FOLLOWERS` (региональные, PR #317). Следствия:

1. **Креды идут через владельца инфраструктуры.** Чтобы подключить пользователя, кто-то должен передать логин и пароль администратору — по любому каналу это утечка секрета в переписку. Ровно этого мы избегали при выдаче PAT (#228), сделав self-service.
2. **В `.env` оказываются ЧУЖИЕ личные пароли.** В текущем кейсе RU-follower — личный аккаунт члена семьи пользователя, а не сервисный ящик. Такому паролю не место в общем конфиге прода.
3. **Не масштабируется.** Приглашения follower'а в LibreLinkUp работают **только внутри региона** (ограничение Abbott): EU-аккаунт `dr@botkin.health` не видит RU-пациента в принципе. Значит каждому региону нужен свой follower, и каждый новый регион — это ручная правка `.env` + пересоздание контейнера.
4. **Изменение `.env` требует пересоздания контейнера** (`env_file:` в compose запекает переменные при create, `docker restart` недостаточно) — то есть подключение одного пользователя означает передеплой.

## Что уже есть

- **Мультирегиональность готова** (#317, в проде с 19.07): формат `LLU_FOLLOWERS`, `_resolve_api_url()` по региону, изоляция token-cache и backoff по регионам, `collect_rows_all()` с изоляцией сбоев одного follower'а от остальных.
- **Онбординг есть**: `/connect_cgm` (`telegram-bot/handlers/connect_cgm.py`, 153 строки) — сейчас показывает инструкцию «пригласи `FOLLOWER_EMAIL`» и до 10 минут поллит `get_patients()`, чтобы поймать новое приглашение и записать `patient_id` → `cgm_connections`.

Нужен, по сути, один недостающий кусок: **источник кред follower'а из БД, а не только из env**, и диалог для их ввода.

## ⚠️ Важное: механизма шифрования секретов в проекте нет

Проверил перед тем, как писать (спрашивал, каким механизмом шифровать — оказалось, брать нечего):

| Что | Как хранится сейчас |
|---|---|
| `users.encrypted_openai_key`, `encrypted_anthropic_key` | колонки есть, но **не читаются и не пишутся нигде** — мёртвый код |
| `users.garmin_password` | **plaintext**, комментарий в модели «encrypted in production» не реализован (`core/health/garmin_data.py:267` читает как есть) |
| `personal_access_tokens.token` | **plaintext** (не хэш) — осознанно, токен нужен для сравнения при обмене на JWT |

Утилиты `encrypt`/`decrypt` в проекте нет, `cryptography` в зависимостях как транзитивная. Поэтому шифрование — часть этого proposal, а не «переиспользуем существующее».

## Предложение

### 1. Утилита шифрования: `core/infra/secrets.py`

```python
def encrypt_secret(plain: str) -> str   # → "v1:<fernet-token>"
def decrypt_secret(blob: str) -> str
```

- **Fernet** (`cryptography.fernet`) — AES-128-CBC + HMAC, ключ из env `SECRETS_KEY` (32 байта base64url).
- Префикс версии `v1:` в самой строке — чтобы ротация ключа/алгоритма позже не потребовала миграции данных.
- Нет `SECRETS_KEY` → `encrypt_secret` **падает явно**, а не пишет plaintext молча. На тестах ключ подставляет `conftest.py` (как уже делается для dummy-ключей LLM).
- Почему не pgcrypto: тесты идут на SQLite in-memory, а расшифровка нужна в питоне (импортёр читает креды перед сетевым вызовом) — держать логику в БД смысла нет.

### 2. Модель: таблица `cgm_followers`

Отдельная таблица, а не колонки в `cgm_connections`: связь «один follower → много пациентов» (один аккаунт может наблюдать несколько человек), и права на неё нужны строже, чем на маппинг `patient_id`.

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | BigInteger PK | |
| `owner_user_id` | BigInteger FK → `users.telegram_id` | кто подключил (аудит + RLS) |
| `region` | String(8) | `RU` / `EU` / … — как в `LLU_FOLLOWERS` |
| `email` | String(255) | логин follower-аккаунта |
| `password_enc` | Text | `encrypt_secret(пароль)`; **имя колонки говорит, что внутри шифр** |
| `label` | String(100), null | человекочитаемая метка («аккаунт жены») |
| `created_at` / `last_ok_at` / `last_error` | | диагностика: когда последний раз логин прошёл и что упало |
| `revoked_at` | DateTime, null | отзыв без удаления строки (симметрично PAT) |

Индексы: `(region)` для выборки активных, `(owner_user_id)`, уникальный `(region, email)` — чтобы один и тот же аккаунт не завели дважды.

### 3. Точки интеграции

**а) `scripts/import/librelinkup.py::_extra_followers()`** — сейчас читает только `LLU_FOLLOWERS`. Становится: сначала БД (`SELECT … FROM cgm_followers WHERE revoked_at IS NULL`), затем env как fallback и bootstrap. Порядок именно такой: БД — источник истины, env остаётся для локальной отладки и для primary-аккаунта. Дедупликация по `(region, email)`, чтобы одна и та же запись из двух источников не логинилась дважды (иначе лишние логины = риск Cloudflare 476).

**б) `telegram-bot/handlers/connect_cgm.py`** — новая ветка. Сейчас поток одношаговый (инструкция + поллинг), FSM в нём нет, поэтому добавляем `StatesGroup`:

```
/connect_cgm
├── «Пригласить наш follower» (текущий путь, EU) — без изменений
└── «Свой follower-аккаунт» (новый, для RU и любого другого региона)
        ├── ждём email        → валидация формата
        ├── ждём пароль       → СРАЗУ удаляем сообщение (bot.delete_message)
        ├── проверяем логин   → pylibrelinkup, регион из выбора
        │     ├── не прошёл  → показать причину, не сохранять
        │     └── прошёл     → encrypt_secret + INSERT, показать список видимых patient_id
        └── предложить привязать себя к найденному patient_id → cgm_connections
```

Ключевые детали:
- **Сообщение с паролем удаляется до записи в БД**, а не после — если запись упадёт, пароль всё равно уже не висит в чате.
- Проверка логина **до** сохранения: не плодим записи, из-за которых ночной sync будет ловить 476 на неверных кредах и уходить в backoff.
- В подтверждении показываем только email и регион; пароль не отображаем и не логируем нигде (`logger.debug` в том числе).

**в) `/my_connections`** — добавить раздел «CGM-followers» с `revoke`, симметрично отзыву PAT.

### 4. Миграция

Одна ревизия: `create_table("cgm_followers")` + индексы. `down_revision` = актуальный head на момент PR. Данных не переносим: текущий `LLU_FOLLOWERS` продолжит работать через fallback, миграция кред в БД — по желанию, командой в боте.

⚠️ Помню про грабли: **миграции накатываются отдельным ручным workflow, а не при деплое** — в описании PR это будет явно указано отдельным пунктом.

## Безопасность

| Риск | Мера |
|---|---|
| Пароль остаётся в истории чата | удаляем сообщение сразу после чтения; в инструкции предупреждаем, что бот его удалит |
| Пароль утечёт в логи | не логируем ни email+пароль вместе, ни `password_enc`; в API-ответах поле не отдаём вовсе |
| Компрометация БД | `password_enc` бесполезен без `SECRETS_KEY` из env (разные носители — БД в volume, ключ в конфиге) |
| Чужой пользователь увидит креды | выборка по `owner_user_id` + RLS, как для остальных пользовательских таблиц |
| Утечка через дампы БД | ⚠️ **открытый вопрос:** ночные `pg_dump` в бэкапах будут содержать `password_enc`. Он зашифрован, но если `SECRETS_KEY` попадёт в тот же бэкап-архив — защита нулевая. Предлагаю держать ключ **только** в `/opt/botkin/.env` и не включать env в архивы бэкапов; нужно подтверждение, что сейчас так и есть |

## Тесты

- `encrypt_secret`/`decrypt_secret`: round-trip, отказ без `SECRETS_KEY`, префикс версии, что шифр отличается при повторном вызове (Fernet добавляет IV).
- `_extra_followers`: приоритет БД над env, дедуп `(region, email)`, игнор `revoked_at IS NOT NULL`, работа без БД (только env).
- Хендлер: пароль удаляется из чата; при неверных кредах записи в БД нет; при верных — `password_enc` не равен plaintext.
- Существующий EU-путь `/connect_cgm` не сломан (регресс).

## Объём

Оценка: ~4 файла кода + миграция + ~15 тестов. Утилита шифрования и хендлер — основное; правка `_extra_followers` небольшая.

## Открытые вопросы к владельцу инфраструктуры

1. **`SECRETS_KEY`** — генерируешь и кладёшь в прод-`.env` ты; ротацию делаем сменой префикса (`v2:`) с чтением обоих. Ок?
2. **Бэкапы** — подтверди, что `pg_dump`-архивы не включают `.env`, иначе шифрование теряет смысл (см. таблицу рисков).
3. **Мёртвые колонки** `encrypted_openai_key`/`encrypted_anthropic_key` — снести отдельным PR или оставить? Как только появится настоящий `encrypt_secret`, их можно либо задействовать, либо удалить, чтобы не путали.
4. **`garmin_password` в plaintext** — переводить на `encrypt_secret` тем же PR или отдельной задачей? Отдельной, по-моему, чище: другой домен, другие тесты.
